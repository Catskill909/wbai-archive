# Pacifica JSON front-end feeds — analysis and migration path

**Status: analysis only. No code has been written and nothing in the app reads
these files.** This documents what the feeds actually contain, what they would
replace, and the order in which to adopt them — so that when a cloned station
needs them the design argument is already settled.

**WBAI is not the target and will not be migrated.** Its archiver and confessor
are too old to emit these files; that is the whole reason this is a *second*
source rather than a replacement. WBAI stays on the scrape + `/xml/` path
documented in [UPSTREAM.md](UPSTREAM.md). This is for the clones — KPFT today,
KPFK and WPFW next.

Everything below was measured against the live files on **2026-08-08**, not read
off a spec sheet. Pacifica's engineer sent a field-level spec and sample output
with the original mail; **reconcile this against that document before building** —
where they disagree, the spec states intent and this states behaviour, and both
are worth knowing.

---

## 1. The endpoints

Four files, two per stream, regenerated by cron (`Last-Modified: 00:00:01` on the
catalogs — the now-playing pair moves continuously).

| URL | Bytes | Shape |
|---|---|---|
| `https://archive.kpft.org/fe_feed/fe_catalog_kpft.json` | 355 KB | `{updated, shows[267], episodes[937]}` |
| `https://archive.kpft.org/fe_feed/fe_catalog_kpfthd3.json` | 845 KB | `{updated, shows[318], episodes[2945]}` |
| `https://archive.kpft.org/fe_feed/fe_nowplaying_kpft.json` | 407 B | `{updated, current, track, next}` |
| `https://archive.kpft.org/fe_feed/fe_nowplaying_kpfthd3.json` | 482 B | same |

All four answered `200 application/json`, served by Apache with `Last-Modified`
and `Accept-Ranges`. **`If-Modified-Since` therefore works**, which matters:
`fetchFeed`'s conditional-request machinery transfers unchanged.

**Two streams, not one.** `kpft` is the broadcast signal; `kpfthd3` is a second
HD subchannel with its own shows, its own episodes and — importantly — its own
retention policy (§4). A station on this backend may have one stream or several.
Whatever gets built must take the stream id as configuration, not assume one.

## 2. `fe_catalog_*.json`

```jsonc
{
  "updated": 1786147201,          // epoch seconds, when the cron ran
  "shows":    [ /* the programme directory */ ],
  "episodes": [ /* the audio */ ]
}
```

### `shows[]` — 267 records, every field present on every record

| Field | Empty | Notes |
|---|---|---|
| `altid` | 0 | the slug. Joins `episodes[].altid` and `nowplaying.current.altid` |
| `name` | 0 | **HTML-escaped** (`Latino Politics &amp; News`) |
| `host` | 33 | |
| `description` | 55 | **HTML-escaped**, long form |
| `shortDescription` | 74 | one line |
| `url` | 227 | |
| `facebook` / `twitter` / `tumblr` | 250 / 260 / 266 | almost always empty |
| `photoUrl` | 129 | absolute, on `confessor.kpft.org` |
| `category` | 0 | station-specific string vocabulary — see §6 |

Fields are always *present*; they are empty strings when unset, never `null`.
That is a pleasant contract: no key-existence checks needed, only truthiness.

**101 of 267 records carry HTML entities** in `name` or `description`. Our
existing `unescapeHtml()` in `server.js` already covers the set observed
(`&amp; &lt; &gt; &quot; &#039;`). Use it; do not render these raw.

### `episodes[]` — 937 records, every field present

| Field | Type | Notes |
|---|---|---|
| `id` | number | archiver's own episode id, e.g. `8740009`. Stable, unique |
| `altid` | string | joins to `shows[]` — **0 orphans in 937** |
| `airDate` | number | epoch seconds |
| `durationSec` | number | **0 on 307 of 937 (33%)** — see §6 |
| `expires` | number | epoch when the mp3 goes away — see §4 |
| `mp3Url` | string | absolute, on `archive.kpft.org` |
| `vtiUrl` | string | WebVTT cue sheet — see §5 |
| `type` | string | only ever `"Music"` or `"Talk"` |

**There is no episode title and no episode description.** An episode is a show
id plus a timestamp. Titles must be composed (`"<show name> — <weekday, date>"`),
which is exactly the shape WBAI's XML already hands us
(`"Democracy Now!  - Thursday, August 6, 2026"`), so the app's search and rail
behave the same. Per-episode blurbs, which the XML path *does* supply as
`episodeDesc`, simply do not exist here — see §6.

**The mp3 filename encodes the air date in station-local time**
(`kpft_260807_150000borderradio.mp3`), identical in convention to WBAI's
(`wbai_260806_080000dn.mp3`). Checked 400 episodes against `airDate` rendered in
`America/Chicago`: **zero mismatches.** So the filename is a usable cross-check,
but `airDate` is authoritative and there is no reason to parse the name.

## 3. `fe_nowplaying_*.json`

```json
{
  "updated": 1786147441,
  "current": { "altid": "jambanhour", "name": "The JamBand Show", "host": "Matt Appel",
               "photoUrl": "https://confessor.kpft.org/pix/jambanhour_med_347.jpg",
               "startTime": 1786143600, "endTime": 1786150800 },
  "track":   { "song": "Talk", "artist": "Talk", "album": null, "label": null,
               "startTime": 1786147398 },
  "next":    { "altid": "midnibeatznbuzz", "name": "Beatz &#039;n Buzz",
               "host": "Skyla Dawn", "startTime": 1786150800 }
}
```

This is **richer than what WBAI's confessor gives us** and is the most immediately
valuable of the four files:

- `endTime` on the current show — a real progress bar for the live player,
  instead of inferring the slot length.
- `next` — "up next" without deriving it from the schedule.
- `track` — **live song/artist/album/label**. We have no equivalent today at all.
- Both `current.altid` and `next.altid` join cleanly to `shows[]`, so the live
  player can reach the show sheet and its past episodes.

Note `track` uses `null` for unset fields, where `shows[]` uses `""`. Two
different empty conventions in one product; handle both.

## 4. `expires` — the field that answers a question we had to measure by hand

Each episode publishes its own deletion date. This is the single most useful
field in the catalog, because it is the thing we currently have to *infer*.

Measured retention:

| | kpft | kpfthd3 |
|---|---|---|
| airDate range | 2026-06-09 → 2026-08-07 (60 days) | **2021-05-16** → 2026-08-07 (1910 days) |
| retention (median) | 60 days | 4720 days |
| `expires` = `2147483647` | 0 | **2316 of 2945** |
| already expired in the file | **0 of 937** | **0 of 2945** |

Two things follow.

**`expires: 2147483647` is INT32_MAX and means "never".** It is not a date in
2038; it is the sentinel a 32-bit `time_t` produces for "no expiry". Treat any
`expires` at or near that value as permanent rather than rendering "expires
2038-01-19" to a listener.

**The catalog is self-pruning: not one expired episode appeared in either file.**
So the feed is a list of *playable* audio, which is a stronger guarantee than the
XML path gives — there we hold items whose mp3 may or may not still exist and
find out on tap.

This also bears directly on the accumulation change made on 2026-08-07
(`mergeFeedItems`, see [UPSTREAM.md](UPSTREAM.md)). Under the XML path we keep
episodes after upstream forgets them, because the audio outlives the listing and
nothing tells us when it will stop. **Here we are told.** A JSON-mode station
should therefore keep accumulating — a 60-day window is still a window — but it
can also mark a retained episode as expired instead of discovering a `404` when
someone taps it. That is a better experience than either source alone gives
today, and it is worth building deliberately rather than inheriting by accident.

## 5. `vtiUrl` — a per-episode track timeline

`https://archive.kpft.org/cue/8740009.vti` returns **WebVTT** (4 KB):

```
WEBVTT

1
00:00:-5.000 --> 00:00:45.000


2
00:00:46.000 --> 00:02:04.000
Border Radio<br>
<i>The Blasters</i>
```

Cue payloads are song title and artist wrapped in HTML. This is a genuine
feature nobody has asked for yet: a scrubable track listing on a music episode,
and it is `kind="metadata"` on an `<audio>` element away from working.

⚠️ **The first cue's timestamp is `00:00:-5.000` — negative, and invalid WebVTT.**
A strict parser (including the browser's own `TextTrack`) rejects the malformed
cue and may discard the file. Anything built on this needs a tolerant parse or a
pre-clean, and the malformation should go back to Pacifica as a bug.

Not on the critical path. Do not let it delay §8.

## 6. What this source does *not* give us

Honest ledger, because three of these are regressions against the XML path.

1. **`durationSec` is 0 on a third of episodes** (307/937 kpft, 249/2945 hd3).
   The XML path has the same weakness but the *listing* backstops it with an
   `HH:MM:SS` string; here there is no second opinion. Duration drives the
   player's scrub bar and `schedLenMin()` in the derived schedule, so a third of
   rows arriving with no length is the single biggest gap. Options: accept it
   and let the `<audio>` element report duration on load (works, but only once
   playback starts), read it from the mp3's headers with a range request, or ask
   Pacifica why it is unset. **Ask first.**
2. **No per-episode description.** The XML gives `episodeDesc`; this gives
   nothing below show level. Partly offset by §7's win on show descriptions.
3. **No `bytes`.** The XML enclosure carries it. Minor.
4. **Categories are a station-specific string vocabulary**, 11 values on kpft
   and a *different* 11 on kpfthd3 (`Community Access` / `News Special` vs
   `Public Access` / `Special Program`). Our app has a fixed 7-key palette
   (`CATS` in `app.js`), and `CAT_MAP` in `server.js` maps WBAI's *numeric* ids
   onto it. A JSON station needs its own mapping, and — since this repo is a
   template — that mapping belongs in **configuration, not a code edit**. A
   station whose category is unmapped must fall back to `special`, never crash.
5. **No wall-clock string.** Only epoch `airDate`. Not a real gap: `STATION_TZ`
   and `secToDateText()` already exist in `server.js` for exactly this, and the
   client's `schedWall()` deliberately parses `dateText` so it needs no timezone
   of its own. Set `STATION_TZ=America/Chicago` and it works.
6. **No schedule grid — and this one is worth pushing back on.** The catalog is
   `shows[]` + `episodes[]` and nothing else; there is no day/time grid, no
   recurrence, no alternation. The now-playing file leaks the thinnest possible
   slice (`current.endTime`, `next.startTime`) and stops there.

   **Pacifica's own scheduling tool has all of this** — alternating weeks and
   drag-and-drop scheduling included. It simply is not exposed in the feed. So
   we derive the week from observed air times (`deriveSchedule`) not because the
   information does not exist, but because the system that holds it does not
   publish it.

   That derivation is exactly what forces the heuristic in §7.7 of
   [schedule-dev.md](schedule-dev.md): with only air times to look at, a show
   that was *replaced* and a show that *alternates fortnightly* produce
   identical evidence, and we resolve it with a 14-day staleness rule that takes
   two weeks to settle. **A `schedule[]` array in the catalog would delete that
   entire problem** — not improve the guess, remove the need to guess. See §9.1;
   it is the highest-value thing we could ask for.

## 7. What it replaces, and why it is worth doing

Today, per station, the app assembles its listing from **three** upstream
sources plus a fourth for live:

| Today | In JSON mode |
|---|---|
| Scrape `archive2/` HTML (~950 KB), parse a table | — |
| Up to **125 conditional `/xml/` fetches** per sweep | — |
| `/api/showinfo` harvest, *only while a show is on air* | — |
| now-playing proxy | one 407-byte file |
| | **one 355 KB catalog + one now-playing file** |

Three specific wins:

- **The show directory arrives complete, in one request.** Today descriptions
  are harvested opportunistically while a show is on air, which is precisely why
  production served blank descriptions for a week after a deploy (CLAUDE.md §4).
  That entire failure mode disappears — `shows[]` has all 267 on every fetch.
- **Archive depth in one request.** 937 episodes over 60 days, against the
  XML path's hard cap of 5 items per feed.
- **No HTML parsing anywhere.** The scrape is the most fragile thing in the
  stack; a JSON station never runs it.

## 8. Migration path

The engineer's framing is right and should be preserved: **opt-in per station,
nothing else in the stack changes.** That claim is true if and only if the
adapter's output is the app's existing row shape. Make that the contract.

### The seam

`getArchive()` returns `{rows, ...}`, and *everything* downstream —
`deriveSchedule`, the routed Show/Past episodes modal, search, the studio, and
usage counting — consumes those rows and nothing else. So the row is the
interface, and a JSON station swaps only what produces it.

Target mapping, field by field:

| row field | from | notes |
|---|---|---|
| `id` | `episodes[].id` | already unique and stable |
| `sho` | `episodes[].altid` | |
| `title` | `shows[].name` + `airDate` | composed; unescape first |
| `dt` | `episodes[].airDate` | |
| `dateText` | `secToDateText(airDate)` | needs `STATION_TZ` |
| `durationSec` | `episodes[].durationSec` | **0 a third of the time — §6.1** |
| `length` | `secToHms(durationSec)` | empty when duration is 0 |
| `daysLeft` | `expires` − now | *better* than today's scraped value; mind the INT32_MAX sentinel |
| `mp3` | `episodes[].mp3Url` | |
| `cat` | `shows[].category` → 7-key palette | per-station map, in config (§6.4) |
| `host` | `shows[].host` | |
| `photo` | `shows[].photoUrl` | |
| `episodeDesc` | — | does not exist (§6.2) |
| `bytes` | — | does not exist (§6.3) |
| `hasRSS` / `rss` | — | not meaningful in this mode |
| `source` | `'json'` | new value alongside `listing` / `feed` / `feed-only` |

### Phases

1. **Config only.** One env var naming the catalog, one the now-playing file —
   e.g. `PACIFICA_CATALOG_URL` / `PACIFICA_NOWPLAYING_URL`. Unset means today's
   behaviour, byte for byte. Add both to `.env.example` in the same commit; that
   file is the station-setup contract (CLAUDE.md §5). Resist a third var for the
   stream id — the URLs already name it.
2. **An offline adapter with a fixture, before any wiring.** `fe_catalog` →
   rows, as a pure function, with a checked-in sample and a suite in `npm test`.
   The six offline suites already there are the pattern. Do this *first* — it is
   the only piece that can be proven without access to a station.
3. **Wire it into `getArchive()` behind the env var.** A JSON station skips the
   scrape and the feed sweep entirely; it does not run them and ignore the
   result.
4. **Now-playing second, and separately.** It is the highest-value file (§3) and
   the lowest-risk change, but the live player is the most-broken-twice part of
   this app — read `live-audio-pattern.md` and `big-audio-bug.md` before going
   near it, and add nothing to `barMode`.
5. **`expires`-aware retention** (§4), once rows are flowing.
6. **`vti` track timelines** (§5), last, if ever.

### Invariants that must survive

- **Row shape is the contract.** If the adapter emits anything else, the
  "nothing else changes" promise is void and the schedule, rail and studio all
  need edits.
- **`hasRSS` selects what to *fetch*, never what to *publish*** — the JSON
  equivalent is that a show with no episodes is not a listing row. 182 of 267
  kpft shows have zero episodes; they are directory entries, not programming.
- **One env var, not three** (CLAUDE.md §5). This is a template.
- **Never let a JSON station silently fall back to the scrape.** `archive2` does
  not exist for KPFT; a fallback would produce a confusing failure instead of a
  clear one.

## 9. Questions for Pacifica

1. **Can the schedule be added to the catalog?** The scheduling tool already
   holds it — recurring shows, alternating weeks, the lot — but none of it
   reaches the JSON. A `schedule[]` of `{altid, weekday, startMin, durationMin,
   recurrence}` would let us *state* the week instead of inferring it from air
   times, and would remove the fortnightly-alternation guesswork described in
   §6.6 outright. **Ask for this first; it is worth more than the rest
   combined.**
2. **Why is `durationSec` 0 on a third of episodes?** Biggest gap (§6.1).
3. **Is `expires: 2147483647` officially "never"**, or an overflow that may be
   corrected later? Behaviour differs (§4).
4. **The `.vti` files open with an invalid negative timestamp** (`00:00:-5.000`),
   which strict WebVTT parsers reject (§5).
5. **Is the `category` vocabulary per-station or Pacifica-wide?** kpft and
   kpfthd3 already differ, which suggests per-station and therefore per-station
   mapping forever (§6.4).
6. **How often is the catalog rebuilt?** Measured 2026-08-08: **now-playing
   regenerates about once a minute** (`Last-Modified` 00:12:02, read at
   00:12:04 — excellent). The **catalog** was still stamped `00:00:01` twelve
   minutes past the hour, which is consistent with hourly *or* nightly and
   cannot be told apart from two readings. It matters: if it is nightly, an
   episode airing at 09:00 does not appear until the next day, which is much
   staler than the XML path. Confirm before choosing a TTL.
7. **Is there an index of available stations/streams**, or is each station's URL
   knowledge that has to be configured by hand?

## 10. A third candidate: our own backend

Pacifica's JSON is not the only alternative to the scrape, and this doc should
not read as though the choice is binary. **StationDock**
(<https://radio.supersoul.top/features.html>) is our own product and covers the
same ground as the archiver/confessor pair: scheduled recording off Icecast,
automated podcast publishing, now-playing, and **a public JSON API with ten
endpoints** — now playing, schedule, shows, stream status, recordings archive,
podcast feed URLs, all paginated. **PodFeed Studio**
(<https://podcast.supersoul.top/features.html>) covers the other half: RSS
aggregation, feed cloning to self-hosted audio, validation.

Worth writing down because it would fix, at the source, the two weaknesses this
document spends the most words working around:

- **The schedule is reachable, not just recorded.** To be clear about where the
  problem actually is: Pacifica's scheduling tool *also* has recurring and
  alternating-week scheduling (§6.6) — it simply does not publish any of it, so
  we are left inferring the week from air times and paying for that with the
  heuristic in §7.7 of [schedule-dev.md](schedule-dev.md). **The gap is
  publishing, not capability.** It happens to be trivially closable on a backend
  we own, and merely an ask on one we do not (§9.1). Either way the fix is the
  same shape: state the schedule instead of guessing it.
- **Duration is known exactly.** It made the recording. Compare §6.1, where a
  third of Pacifica's episodes arrive with `durationSec: 0` and no fallback.

It also supplies things no upstream here does at all: per-episode play
analytics, song recognition, stream health.

**The reason all three are viable is the seam in §8.** Everything downstream of
`getArchive()` consumes rows. Pacifica JSON, StationDock's API and the existing
scrape are three producers of one shape — so this is a question of which adapter
a station configures, not a rewrite. Keep it that way: the moment source-specific
knowledge leaks past the adapter into `app.js` or the studio, the portability
that makes this a template is gone.

No adapter exists for StationDock either. Same phase order as §8 applies, and
the offline-adapter-with-a-fixture step matters more here, not less.
